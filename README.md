# Reverie in Rain

> 2D 类银河城动作游戏 · 自研 Unity GameFramework
> 框架设计说明 v0.3（仅框架层）

## 1. 框架目标

《Reverie in Rain》是一款 PC 端 2D 类银河城动作游戏。项目不直接套用现成框架，而是自研一套轻量 GameFramework，作为整个游戏的底层支撑。

框架只做三件事：

1. **统一生命周期**：所有全局模块由框架注册、初始化、驱动和释放，避免单例散落各处、初始化顺序混乱。
2. **屏蔽底层细节**：把资源加载、对象创建、UI 打开、输入读取、存档读写等 Unity 原生操作封装成稳定接口，业务层不关心 AssetBundle、协程、Input System、PlayerPrefs 等实现。
3. **保持业务无关**：框架代码中不出现玩家、Boss、房间等游戏概念，可整体迁移到其他项目。

## 2. 技术选型

| 项 | 选型 | 说明 |
|-|-|-|
| 引擎 | Unity 6.3.11f1（6000.3.11f1） | 当前工程实际版本 |
| 渲染管线 | URP 2D（17.3.0） | 2D 光照与后处理 |
| 输入 | 新 Input System（1.19.0） | 键鼠 / 手柄统一 |
| UI | UGUI（2.0.0） | 2D 界面 |
| 2D | Tilemap / 2D Animation / Sprite Shape | 地图与角色动画 |
| 异步 | 协程（Coroutine） | 不使用 UniTask / async-await |
| 资源 / 热更 | 自研 AssetBundle + AB 插件包 | 不使用 Addressables |
| 逻辑热更 | XLua | 后续接入 |
| 测试 | Unity Test Framework（1.6.0） | EditMode 单测 |

**选型说明：**

- **AssetBundle（自研 + 插件包）**：资源与热更采用自研 AssetBundle 方案，后续导入 AB 插件包辅助打包与依赖分析。不使用 Addressables——面向的国内开发环境仍以 Unity 2021–2022 LTS 为主流，Unity 6 的本土工具链与生态适配尚未成熟，自研 AB 更可控、可迁移、可跨版本维护。
- **协程（Coroutine）**：所有异步逻辑统一走协程，不引入 UniTask。团队现有协程知识即可覆盖，降低学习成本，保持框架轻量；协程宿主由框架的全局入口统一提供。

## 3. 分层约定

| 层 | 内容 | 依赖方向 |
|-|-|-|
| 框架层 | 本文描述的 20 个模块 | 不依赖业务 |
| 业务层 | 玩家、敌人、战斗、地图、成长、叙事 | 只依赖框架接口 |
| 内容层 | Prefab、美术、音频、配置表、Lua | 只通过地址被引用 |

约束：业务层不直接使用 `Resources.Load`、`GameObject.Find`、`PlayerPrefs`、`Input.*`（旧输入）等 Unity 原生 API，统一走框架；模块之间通过事件与接口通信，不互相持有内部实现。

## 4. 模块设计

框架共 20 个模块，按初始化依赖分为五层。其中「单例」「状态机」为纯模式/基类，不参与运行时初始化，供各模块与业务直接使用。

### 4.1 基础层（最先初始化）

#### 4.1.1 单例（Singleton）

为框架内的全局模块提供统一的单例基类和访问入口。

- 提供普通单例与 MonoBehaviour 单例两种基类，处理重复实例、跨场景常驻、销毁清理。
- 框架对外只保留一个全局入口，业务通过它获取模块接口，而不是到处写 `Instance`。
- 处理关闭 Domain Reload 后静态字段不复位的复位问题（Enter Play Mode Options）。
- 解决的问题：初始化顺序混乱、重复挂载、场景切换后引用失效。

#### 4.1.2 日志与工具（Log & Utils）

开发期的可观测性与通用工具集合。

- 日志分级（Debug/Info/Warn/Error）、按频道过滤、开发期屏幕输出与文件落盘。
- 通用工具：数学与随机、扩展方法、路径与字符串处理、协程辅助。
- 提供调试面板入口：FPS、内存、当前房间、状态机状态，方便自查与答辩演示。

#### 4.1.3 事件中心（Event）

模块之间解耦通信的总线。

- 以类型区分事件，支持订阅/取消订阅，按 owner 自动退订，避免对象销毁后回调泄漏。
- 倒序遍历派发，订阅者在回调中退订自己不会打乱遍历。
- 战斗热路径事件（伤害数字、音效、震屏）优先用 struct 事件 + 泛型 `EventBus.Get<T>()` 做到零 GC。
- 典型场景：玩家受伤 → HUD 刷新、音效播放、震屏、伤害数字，发送方不需要知道接收方是谁。

#### 4.1.4 状态机（FSM）

管理角色与流程的状态切换（纯模式，供业务直接使用）。

- 提供泛型状态机：状态注册、默认状态、进入/更新/退出回调、条件切换。
- 玩家用于移动、跳跃、冲刺、攻击、受击、死亡；Boss 用于多阶段切换。
- 可选层次状态机，处理“移动中可攻击”这类父子状态。
- 解决的问题：大量 if/switch 堆叠、状态跳转难以维护。

#### 4.1.5 计时器（Timer）

统一由框架 Update 驱动的计时 / 延时 / 周期任务，替代业务各自开协程。

- 支持一次性延时、循环、帧计时，可受 / 不受 Time.timeScale 影响。
- 内部复用计时单元，避免高频计时产生的 GC。
- 典型场景：技能冷却、Buff 持续时间、逐帧伤害、倒计时、延迟派发。
- 解决的问题：计时逻辑散落各处、协程泛滥导致的不可控。

### 4.2 数据层

#### 4.2.1 全局数据（GameContext）

运行时状态的单一事实来源（黑板书）。

- 用键值承载当前 HP、当前房间、游戏时间、已获得能力等全局变量。
- 模块 / 业务通过它读写跨模块共享数据，而非散落静态字段。
- 支持值变化订阅，与存档对接时集中导出 / 恢复。
- 解决的问题：事件只负责“通知”，数据得有地方“存”。

#### 4.2.2 配置（Config）

把数值与规则从代码里挪出来，交给表格。

- 支持配置表加载、按 ID 索引、类型转换与默认值。
- 覆盖玩家参数、敌人参数、掉落、房间、对话、本地化文本等。
- 提供编辑器校验：重复 ID、空引用、非法数值在打包前报错。
- 配置可随热更下发，改数值不需要重新出包。

#### 4.2.3 本地化（Localization）

把所有“给人看的文字”从代码里抽离，做成可切换、可维护、可翻译的数据。

- 文本与代码分离：业务只通过 key 取文本（`Loc.Get("ability.doubleJump")`），文本本体放语言表。
- 按语言分表（zh-CN / en-US …），启动时只加载当前语言，运行中切换后发事件、面板刷新。
- 支持占位符（`“造成 {0} 点伤害”`）与 key 回退、缺失 key 兜底。
- 字体与字形管理：中文字形体积大，做 TMP 字形图集按需烘焙与字体回退链；切换语言时字体联动。
- 语言作为设置项，读 Config 默认值、存 Save 持久化；文本表可随热更下发。
- 编辑器校验：缺失 key、冗余 key、占位符一致性、漏翻译检测（放 Editor 程序集）。
- 与配置的分界：配置管“数值与规则”，本地化专管“文本”，因文本量大、按语言整表切换、翻译工作流而独立。

### 4.3 资源层

#### 4.3.1 热更（HotUpdate）

在不重新打包的前提下更新资源与部分逻辑。

- 资源侧：对比远端版本清单，差量下载 AssetBundle 到本地缓存，校验（hash / 签名）后切换。
- 逻辑侧：通过 XLua 加载 Lua 脚本，支持 UI、配置、数值、关卡逻辑的热修复。
- 负责版本号、下载进度、失败回滚与本地缓存清理。
- 约束：核心战斗与性能敏感逻辑仍用 C#，Lua 只做可热更的部分。

#### 4.3.2 资源（Resource）

统一的资源加载与释放入口。

- 以地址（路径或 Label）加载，支持同步、异步与加载进度。
- 返回资源句柄并做引用计数，谁加载谁释放，归零后真正卸载。
- Editor 下走 AssetDatabase 直接加载，打包后走 AssetBundle，业务代码无需区分。
- 管理包依赖与冗余，为热更提供清单基础；未释放句柄提供 debug 检测。

#### 4.3.3 对象池（Pool）

复用频繁创建销毁的对象，控制 Instantiate 与 GC 开销。

- 按 Prefab 分池，支持预热、容量上限、自动回收与缩容。
- 提供取出与放回回调，对象复用时重置动画、粒子、碰撞等状态。
- 与房间联动：切换房间时可清空场景内池对象；未归还对象提供 debug 检测。
- 典型场景：特效、伤害数字、弹幕、敌人、可破坏物。
- 解决的问题：战斗高峰期频繁创建销毁造成的卡顿与内存碎片。

### 4.4 服务层

#### 4.4.1 输入（Input）

屏蔽底层输入系统，业务只读逻辑动作。

- 屏蔽新 Input System 与手柄 / 键鼠差异，业务只读「移动、跳跃、攻击」等逻辑动作。
- 动作缓冲（input buffer）：提前输入在窗口内仍能触发，是银河城手感的关键。
- 按键重映射与配置持久化；输入屏蔽（切房间 / 过场 / 死亡时锁输入）。
- 典型场景：攻击 / 跳跃的提前输入、手柄键盘统一、菜单导航。

#### 4.4.2 音频（Audio）

统一管理 BGM 与音效播放。

- BGM 支持淡入淡出、跨场景延续、按区域切换。
- SFX 走 AudioSource 池，限制同帧同名音效数量，避免爆音；支持 2D 空间衰减。
- 按总线分组（Master / BGM / SFX / UI），统一音量与静音设置，并写入存档。
- 与事件中心配合：战斗事件直接触发音效，业务层不需要持有 AudioSource。

#### 4.4.3 UI 框架（UI）

统一管理 UGUI 面板的打开、关闭、层级与刷新。

- 面板基类统一生命周期：创建 → 打开 → 刷新 → 关闭 → 销毁。
- 分层管理：场景层、HUD、窗口、弹窗、提示、加载，避免 Sorting Order 混乱。
- 窗口入栈，返回键逐层关闭；支持异步打开与打开动画。
- 面板只监听事件刷新数据（脏标记 / 事件），不每帧轮询业务状态。

#### 4.4.4 存档（Save）

统一收集、序列化与恢复游戏进度。

- 需要持久化的模块实现统一接口并注册，存档时由框架集中收集，避免各模块各存各的。
- 支持多存档槽、自动存档与手动存档、版本号与迁移逻辑。
- 写入采用临时文件替换，防止中途崩溃损坏存档；保留备份槽；设置与进度拆分为独立文件。
- 存档内容：位置、房间、生命/能量、能力、地图探索、Boss、NPC、设置等。

#### 4.4.5 场景（Scene）

薄封装的场景加载 / 卸载服务，是房间与流程共同的地基。

- 统一同步 / 异步加载、卸载、激活场景，封装 `SceneManager` 与加载进度。
- 供房间（切地图单元）与游戏流程（切 Boot/主菜单/游玩）复用，避免两处各自写场景逻辑。
- 与资源模块配合：场景作为资源由 Resource 加载；与过场配合：加载期间走过渡界面。

### 4.5 玩法层（最后装配）

#### 4.5.1 实体（Entity）

场景中游戏对象的通用骨架，是对象池与事件中心的载体。

- 统一生命周期：Spawn → Init → Show → Update → Hide → Release。
- 与对象池联动：池化对象（子弹、特效、敌人）通过 Entity 接口统一取出 / 放回并重置状态。
- 与事件中心联动：按 owner 自动订阅 / 退订，对象销毁后不漏回调。
- 可选 `EntityComponent` 组件接口（普通组件 + 接口约束，非 ECS）；具体 Player/Enemy/NPC 属业务层，继承 Entity。
- 解决的问题：池化对象与事件订阅的生命周期管理散落各处。

#### 4.5.2 房间（Room）

管理类银河城的地图单元与切换流程。

- 房间数据描述：ID、场景、包围盒、门、敌人、存档点、相机边界。
- 负责房间加载/卸载、玩家从哪扇门进入、落点与朝向、相机边界切换。
- 切换时配合过场（淡入淡出、冻结输入），避免加载过程中的操作与穿帮。
- 对外提供当前房间、已探索房间与连通关系（含捷径），供地图系统与存档使用。

#### 4.5.3 相机（Camera）

2D 相机独立管理，避免相机逻辑散落各处。

- 跟随平滑、房间边界约束、镜头过渡、锁定战斗区域（Boss 房锁镜头）。
- 与房间联动：进入房间时切换相机边界。
- 震屏由事件中心驱动，业务不直接操作相机。
- 解决的问题：边界穿帮与手感不一致。

#### 4.5.4 游戏流程（GameFlow）

应用级流程状态机，是框架的“外壳”。

- 流程：Boot → Logo → 标题 → 主菜单 → 选档 → 载入 → 游玩 → 暂停 → 结算。
- 负责场景 / 流程的顶层调度与切换，由全局入口装配后启动。
- 与房间互补：房间管“地图单元”，流程管“应用状态”。
- 解决的问题：主菜单、暂停、死亡结算等应用级流程无归属。

## 5. 模块关系

- 单例与全局入口负责装配，其余模块不互相直接引用。
- 事件中心是模块间的主要通信方式；资源、对象池、音频、UI、输入由业务层直接调用。
- 状态机、计时器为纯模式 / 基础组件，供各模块与业务直接使用，不参与线性初始化。

**启动顺序（初始化）：**

```
日志与工具 → 事件中心 → 计时器 → 全局数据 → 配置 → 本地化 → 热更 → 资源 → 对象池
→ 输入 → 音频 → UI → 存档 → 场景 → 实体 → 房间 → 相机 → 游戏流程
```

- 关闭时逆序释放，先停业务、再释放资源，避免悬空引用。


程序集依赖方向（单向，不可逆）：

```
Game ──► GameFramework.Runtime ──► GameFramework.Core ──► Unity 引擎
                    │
                    └──► GameFramework.Editor（仅编辑器，运行时不可见）
```

- `autoReferenced` 均为 `false`：程序集需显式声明引用，避免隐式引用破坏分层。
- 框架层（Core / Runtime）不引用业务层（Game），编译期即强制「框架不依赖业务」。
